## 1. 프로젝트 맥락

### 최종 목표
표면 상태를 보고 **그 순간 필요한 힘·속도를 결정하는 정책(policy)**을 학습한다.
고정 스펙("힘 3~8N")이 아니라 **조건에 따라 답이 바뀌는 매핑**이 목표.

### 전체 학습 설계 (설계 문서 3장)
```
[BC 정책, frozen]  상태 → a_base (목표힘, 이송속도)
        ↓
[PPO 잔차 정책]    상태 + a_base + 실측힘 → Δa (bound 내 보정)
        ↓
   최종 action = a_base + Δa  →  Isaac Sim PhysX
```
**현재 진행 중인 건 BC 단계뿐.** RL 잔차는 `learning/rl/`로 추후 추가.

### 중요 — 선생님(teacher)이 누구인가
**숙련공 데이터는 존재하지 않는다** (모션캡처 미확보). 따라서:
- 선생님 = 기존 규칙 컨트롤러(`scripts/polishing_v5_modules/`)가 시뮬레이션을 돌린 로그
- BC의 역할 = RL의 **출발점(부트스트랩)** 제공. 실력 개선은 RL 잔차 담당
- 대외 표현: "숙련공 재현"이 아니라 **"규칙 기반 시연 로그로 부트스트랩된, 물리 검증 대상 정책"**

> 참고: 스크립트/규칙 컨트롤러를 선생님으로 삼는 BC는 로봇 학습의 표준 관행이다
> (MPC 복제, privileged policy distillation 등). "BC가 아니다"라고 볼 이유는 없다.

## 3. ✅ 완료 — 1단계: 라벨을 실측값으로 교체 (2026-08-26)

> 아래 원래 계획대로 구현 완료. 추가로 **라벨 스무딩**이 필요했다는 게 실험에서 드러났다:
> - raw `filtered`(t)를 라벨로 쓰면 모델(0.55N)이 "직전 힘 복사" naive 베이스라인(0.32N)보다 나쁘다.
>   스텝 단위 힘 요동은 물리 노이즈라 상태로부터 예측 불가능하기 때문.
> - 라벨을 궤적별 centered rolling mean w=21(≈0.35s)로 스무딩하면 역전: naive 0.63N vs 모델 0.45N.
>   이송속도도 동일 스무딩으로 MAE 131→94mm/s.
> - 해석: BC가 배울 대상은 "그 지점에서 유지되는 부드러운 프로파일"(a_base)이고,
>   순간 요동 대응은 RL 잔차 + 실시간 힘 피드백 담당 — 전체 설계와 일관됨.
> - `prev_force` **입력**은 스무딩하지 않는다 (배포 시 실제 센서값이 들어오므로).
> - 구현: `config.LABEL_SMOOTH_WINDOW`, `extract_dataset.py:smooth_trajectory` (궤적 경계 = 같은 seg 연속 주행 run).
>   raw 실측값은 aux(`raw_force`,`raw_speed`)에 보존 — 평가 그래프에서 사용.
> - 다중 로그 누적도 구현됨: `learning/data/raw/<날짜>/force_log_rail_*.csv` 자동 수집(해시 중복 제거).

### 왜 필요한가 (핵심)

현재 `extract_dataset.py`가 목표힘 라벨을 이렇게 만든다:
```python
target_force = adaptive_target_force(tilt_deg, mode="side" if is_side else "top")
```
그런데 `tilt_deg`(입력 6번)와 `is_side`(입력 9번)는 **이미 신경망 입력에 들어 있다.**
→ 라벨 = 입력의 정확한 결정적 함수 → 네트워크가 새로 배울 정보 0. 규칙을 MLP로 옮겨 담는 것에 불과.

**로그에는 실제로 달성된 힘이 있다.** 확인 결과:
```
[C]  filtered  mean=3.45  std=1.66  min=0.00  max=14.00
[SR] filtered  mean=2.39  std=1.42  min=0.00  max=6.00
```
규칙이 **명령한** 힘은 ~7.4N인데 물리엔진에서 **실제 달성된** 힘은 ~3.45N이다.
이 차이(명령 vs 실제)야말로 시연 데이터의 알맹이고, 어떤 수식으로도 미리 계산할 수 없다.
장인 데이터가 생겨도 라벨은 똑같이 "실제 누른 힘"이 된다. → **지금 방식이 미래와도 일관됨.**

### 구체적 변경 사항

**(a) 목표힘 라벨 교체**
- `adaptive_target_force(...)` 재계산 → 로그의 `filtered` 컬럼 사용
- 참고: `sensor_valid_force`는 **전 구간 0**이다 (물리 센서 비활성, `USE_PHYSICAL_CONTACT_SENSOR=False`).
  `filtered`와 `virtual_force`는 거의 동일 — 제어에 쓰이는 `filtered` 권장.

**(b) 입력에 힘 피드백 추가 — 반드시 1스텝 지연시킬 것**

⚠️ **누수 주의**: 힘을 라벨로 쓰면서 같은 시점 힘을 입력에 넣으면 정답을 그대로 베낀다.
```
입력  = 상태(t) + filtered_force(t-1)     ← 직전 스텝 측정값
라벨  = filtered_force(t)                  ← 이번 스텝 달성 힘
      + feed_speed(t)                      ← 이번 스텝 이송속도
```
이송속도는 힘과 다른 물리량이라 `filtered_force(t-1)` 입력으로 예측해도 누수가 아니다.
오히려 **이게 이송속도 예측이 흩어지는 문제의 해법**이다 (아래 참고).

**(c) 기대 효과**
현재 이송속도 MAE가 88mm/s로 큰 이유: 규칙 코드가
*"접촉력이 정상 범위(`advance_min`~`advance_max`)면 고속 전진(~500mm/s), 아니면 크리프(~30mm/s)"*
로 속도를 정하는데 **힘 정보가 입력에 없어서** 신경망이 두 모드의 중간값만 낸다.
힘 피드백을 입력에 넣으면 이 이중 모드를 학습할 수 있게 된다.
(관련 코드: `agent.py:2094-2117`)

### 수정 대상 파일

## 3.6 v2 — 절대 위치 제거 (2026-08-26 완료)

### 왜
RL은 다른 팀원이 Isaac Lab에서 **"로봇 1대 + 굴곡 오브젝트"**로 진행하기로 결정됨.
`polishing_v5.py`는 단일환경·통짜루프·RMPFlow·3대협조라 병렬 RL(512~2048 env)에 부적합하므로
새 환경을 쓰는 게 맞고, 그러려면 BC가 차량 특정 좌표에 의존하면 안 된다.

### 진단 — BC는 좌표를 외우고 있었다
permutation importance (입력을 섞어 성능 악화를 측정, val 414개):
```
v1:  pos_z +0.129N ← 1위        tilt_deg +0.017N   curvature +0.003N
     "82° 경사면이면 3N"이 아니라 "높이 1.44m면 3N"을 외운 상태
```

### 결과 — 빼니까 오히려 좋아졌다
| 입력 | 힘 MAE | 속도 MAE |
|---|---|---|
| v1 전체 12개 | 0.330 N | 69.7 mm/s |
| **v2 위치제외 9개** | **0.285 N** | **63.3 mm/s** |
| (참고) 기하+피드백 6개 | 0.311 N | 48.2 mm/s |

절대 좌표가 목발 역할을 하며 과적합을 유발하고 있었다.

### 검증 — 의존이 기하 특징으로 옮겨갔나 (핵심 판정)
```
              v2         v1
prev_force  +0.317  ←  +0.117   ↑ 실시간 피드백 의존 급증
is_side     +0.124  ←  +0.006   ↑
progress    +0.087  ←  +0.051   ↑
tilt_deg    +0.040  ←  +0.017   ↑ 기울기를 2.4배 더 봄
curvature   +0.018  ←  +0.003   ↑ 곡률을 7배 더 봄
```
좌표 목발이 사라지자 **기하 특징과 실시간 피드백으로 판단이 이동**했다. 의도한 결과.

### 남은 것
- `normal_x/y`는 월드 축 기준이라 오브젝트 회전 시 달라진다 (`tilt`=`normal_z`만 회전 불변).
  현재 importance가 ~0(normal_x는 -0.010)이라 유지. 전이가 문제되면 6개 입력안 검토.
- 이전 체크포인트는 `checkpoints/bc_mlp_v1_withpos.pt`로 백업돼 있다.

## 3.5 배포 계약 — BC 출력을 어디에 꽂는가 (2026-08-26 확정)

### 문제
출력 이름이 `target_force_n`(목표힘)인데 값은 **실측 달성힘**이었다. 시뮬에는 서로 다른 값이 셋 있다:

| | 정체 | 코드 위치 | 평균 |
|---|---|---|---|
| ① 목표힘 setpoint | 규칙 공식이 뱉는 값 | `agent._target_force` | 5.82 N |
| ② 압입 깊이 `z_offset` | 어드미턴스 제어기가 실제로 움직이는 액추에이터 명령 | `agent.py:2030-2037` | — |
| ③ 실측 접촉력 | 물리엔진 결과 | 로그 `filtered` | 3.12 N |

우리 라벨은 ③이다 (①은 tilt의 결정적 함수라 학습 정보 0).

### 결정
**BC 출력 `contact_force_n`은 배포 시 ①의 자리(`agent._target_force`)에 투입한다.**

### 근거 — 규칙의 목표힘은 물리적으로 도달 불가능하다
```
규칙 명령 평균 5.82N  vs  실측 평균 3.12N   (98%의 스텝에서 명령 > 실제)
시연 압입 포화율 65.7% — 최대 깊이(press_min=0.012)에 붙은 채로도 평균 3.59N
  · C 레일만 보면 73.5%가 포화, 그 상태로 평균 3.27N
```
제어기가 "더 누를 여유가 없는 상태"로 계속 밀고 있었다는 뜻이다. 따라서:
- ①을 복제하면 → 제어기가 계속 깊이 한계에 붙어 있고, **2단계 RL 잔차가 Δ를 줘도
  한쪽 방향(더 누르기)으로는 아무 효과가 없다.**
- ③을 목표로 주면 → 포화되지 않는 지점에 안착해 **양방향 보정 여유**가 생긴다.

### ⚠ 아직 검증 안 됨
이 계약은 **논리와 로그 통계로 정한 것이고, 시뮬에 실제로 연결해 확인한 게 아니다.**
2단계에서 정책을 투입할 때 반드시 확인할 것:
- [ ] BC 목표힘 투입 시 `z_offset` 포화율이 65.7%보다 확실히 낮아지는가
- [ ] 힘 추종 오차(목표 vs 실측)가 규칙 컨트롤러보다 작은가
- [ ] 포화가 남으면 `PRESS_OFFSET_MAX`/패드 강성 재검토 필요

## 5. 다음 작업 — 3단계: 반복 패스 / 종료 판단 (선택)

### 배경
사용자 지적: 장인은 힘·속도뿐 아니라 **"몇 번 왔다갔다 할지"**도 판단한다. 타당한 지적이고,
시뮬에도 이미 **재폴리싱 패스 로직이 구현돼 있다** (`agent.py` `_regen_segs_from_red`,
커버리지 기반 — 안 칠해진 빨간 점이 남으면 그 점들로 경로를 재생성해 재주행).

### 현재 데이터 상황
```
status_log.txt: "재폴리싱_패스_—_구간_11_슬라이딩_시작"  ← SL/SR에서 2건뿐
C 레일 seg 방문 순서: [0,1,2,...,9]  ← 각 구간 1회씩, 되돌아감 0회
```
→ **현재 로그엔 학습에 쓸 반복 데이터가 사실상 없다.** 2단계로 데이터가 쌓인 뒤 착수할 것.

### 설계 시 고려사항 — 행동의 시간 스케일이 다르다
| 행동 | 결정 주기 | 형태 |
|---|---|---|
| 힘, 이송속도 | 매 스텝 (60Hz) | 연속 |
| 반복할까 / 끝낼까 | 구간 종료 시 1회 | 이산 |

두 스케일을 하나의 MLP에 넣으면 어색하다. 선택지:
- **A. 계층적 정책** — 상위(패스 결정) + 하위(순간 제어). 깔끔하지만 정책 2개.
- **B. 종료 head 추가** — 현 MLP에 출력 1개 추가("이 구간 더 닦아야 하나 0~1"),
  구간 끝에서만 읽음. 구조 변경 최소. **권장.**

> 설계 문서 8장에 이미 *"1 에피소드 = 경로의 한 구간, 종료조건(완주/허용치초과/최대스텝)"*
> 이라 적혀 있다. 즉 반복·종료 판단은 **RL 에피소드 설계에서 다루기로 이미 정해둔 항목**이므로,
> BC 단계에서 넣지 않아도 전체 설계가 깨지지 않는다.

## 6. 구현 시 반드시 알아야 할 함정

### ⚠️ (1) CAR_LIFT_Z 보정 — 이미 해결했지만 재발 주의
로그의 `seg` 번호를 좌표로 되돌리려면 `agent.py.__init__`의 경로 로드 절차를
**그대로** 재현해야 한다. 특히 정지 위치 z에 `CAR_LIFT_Z`(0.90m)를 더하는 부분:
```python
# agent.py:30
self.yz_stops = [[float(y), float(z) + CAR_LIFT_Z] for (y, z) in config["yz_stops"]]
```
이걸 빠뜨리면 `filter_safe_waypoints`가 도달 반경(0.35~0.85m) 밖으로 판정해서
**측면 레일(SL/SR) 경로가 전부 사라진다.** 처음에 이 버그로 SL/SR 샘플이 0개였다.

### ⚠️ (2) seg 인덱스는 "빈 구간을 건너뛴 뒤"의 번호
`rail_config.json`의 `yz_stops` 인덱스와 로그의 `seg`가 **다르다.**
경로 파일이 없거나 필터 후 웨이포인트가 0개인 구간은 건너뛰고, 남은 것만 순서대로 0,1,2...가 된다.
반드시 같은 순서로 재구성할 것 (`extract_dataset.py:build_segments` 참고).

### ⚠️ (3) train/val 분할은 (rail, seg) 그룹 단위
샘플을 무작위로 섞으면 연속된 스텝(거의 같은 데이터)이 양쪽에 나뉘어 **누수**가 생긴다.
현재 `train.py:split_by_group`이 구간 통째로 한쪽에만 넣는다. 이 방식 유지할 것.

### ⚠️ (4) 이송속도 이상치는 진짜 데이터다
최대 0.92 m/s가 이상치처럼 보이지만, 규칙 코드의 `POLISH_SPEED_SCALE = 3.0`
설계 속도와 일치하는 정상 동작이다. 필터링하지 말 것.

### ⚠️ (5) 회전속도는 학습 대상이 아니다 (사용자 확정)
`PAD_SPIN_VELOCITY = 314.16 rad/s` 고정. 로그의 `spin` 컬럼은 0/1 플래그이고 전 구간 `1`이라
분산이 0 → 학습 불가. 나중에 상황별 rpm 로직이 생기면 그때 추가.
